### The conflict, and the trap inside it

Upstream `4aa6ffba2` (*sycl: reduce redundant work in Q4_K multi-column MMVQ*, #27062) rewrote the same region of `mmvq.cpp` our GLU-fusion patch extends, and `6703d7894` moved `fusion.cpp`'s includes. `fusion.cpp` was trivial (keep both includes). `mmvq.cpp` needed a real merge: upstream's new `launch_mul_mat_vec_q_reorder_glu` wrapper — which picks `rows_per_sg` from the new `reorder_vec_dot_shared_activations<T>` trait — had to be **kept**, while upstream's Q4_K-only entry function was **dropped** in favour of our type-dispatch version.

**The trap:** our patch's `ncols_dst == 2` branch hardcodes `rows_per_sg = 2`, which was safe when the fused path was Q4_K-only. Upstream now guards that with

```cpp
static_assert(rows_per_sg == 1 || reorder_vec_dot_shared_activations<...>::value);
```

and `shared_activations` is specialised **only for Q4_K**. Extending the fused path to Q4_0/Q8_0/Q2_K/Q3_K/Q5_K/Q6_K with the branch as written is a **compile error**, not a silent slowdown — the `case 2` branch is now `if constexpr`-gated on the trait and pairs at 1 for every other type. Worth remembering the next time upstream generalises a Q4_K-specific fast path: our patches sit directly on top of the code that keeps getting generalised, so each bump needs the *semantics* re-checked, not just a clean `git rebase`.

## 2. Method

Bench slot on **B60 card 2** (`ZE_AFFINITY_MASK=1`, `:8020`, `bench-slot.sh`), production untouched on card 1 throughout. `bench-candidate.py`, standard settings: prefill 3 samples × {500, 2k, 5k, 12k} with `cache_prompt:false`, decode 20 × 300 tokens at temp 0.6 / top-p 0.95 / top-k 20, acceptance from `spec_decode_*` counters, VRAM sampled by `xpu-smi` at 3 s.

Runs were **interleaved per model** (old, then new, back to back on the same slot) rather than blocked by image, so drift between models cannot masquerade as an image effect. This is one pass per arm, not A-B-B-A — per **finding #47** the cross-pass noise floor on this rig is ~4-5 pp, so **any delta under ~15% below is parity, not a result.**

Config per model matches production except context, held at 131072 for all four and `--parallel 1` (prod Ornith is 262144, prod E2B is 196608/12 slots) — the A/B is valid, the absolute numbers are not directly comparable to the production slots or to the 2026-08-21 table.

Raw JSON + driver scripts: [`configs/benchmarks/20260904-b10809/`](../../configs/benchmarks/20260904-b10809/).

## 4. The dropped revert — and why acceptance probably moved

The old image carried a local revert of upstream #28159 (*model : load hparams.n_layer_nextn before n_layer() calls*), added 2026-09-01 because Nemotron misbehaved with it. It was **not carried onto the new base**, because upstream landed `d11b3cc7e` (*model : load relevant arrays with n_layer_all*, #28173) in this window — the follow-up fix that the revert was standing in for.

Consequences, measured:

- **Nemotron loads and runs correctly on the new build without the revert** — MTP head attaches, 100.0% draft acceptance at mean length 7.87, coherent output. The revert is no longer needed.
- **Ornith's acceptance rose 10 pp in the same change.** `n_layer_nextn` is the MTP-head layer count, so a revert that restores the old load ordering plausibly under-configured the head. This is the leading hypothesis for §3's +25% and it is **not confirmed** — an A/B of the new base with and without the revert would settle it, and has not been run.

**Rule this suggests:** a local revert of an upstream correctness fix is a loan, not a fix. Ours cost ~10 pp of acceptance on an unrelated production model for three days, and nothing would have shown it except a bench that measured acceptance on both arms.

## 5. Nemotron: blocked by a GPU engine reset, on **both** builds

Nemotron 30B-A3B is the model the b10742 patch series was built for, and it could not be benched on either image. Both arms died with the same fault on card 2 (`0000:0b:00.0`):

| time (UTC) | image | phase | dmesg |
|---|---|---|---|
| 18:45:17 | old `b10742-patched-a82c13531` | 12K prefill, ~10 min in | `Tile0: GT0: Engine reset: engine_class=ccs, guc_id=8` — `Timedout job ... in llama-server` |
| 18:57:09 | new `b10809-patched-f937ca544` | decode, run 4 of 20, ~6 min in | `Tile0: GT0: Engine reset: engine_class=ccs, guc_id=21` — `Timedout job ... in llama-server` |

The server stays "healthy" and holds its VRAM after the reset; it simply never returns from the in-flight request. Symptom is an indefinite hang, not a crash.

**What this rules in and out:**

- **Not caused by the update.** Identical fault, same engine class, on the pre-existing production image.
- **Not general to the card.** Ornith, E2B and the 26B all completed full runs on the same slot in the same session, before and after both faults.
- **Load-triggered, not idle.** `llamacpp-nemotron` had been up 3 days on `:8011` without a fault; both resets came under sustained bench load within ~10 minutes.
- Consistent with the open GPU-reset investigation (`llamb-mtp fwdloop` reproducer, ~20-50 s to fault) — and with that investigation's note that **both** B60s faulted identically. Coredumps captured to `configs/benchmarks/20260904-b10809/`; the live one is at `/sys/class/drm/card2/device/devcoredump/data`.

`xe-job-timeout.service` (watchdog raised to 10000 ms) is already in place and did not prevent it.

## 8. Stock-upstream control arm — is the engine reset ours or upstream's?

Question from the operator after §5: both faulting images carry our `ggml-sycl` series, so does a **stock upstream** build fault too? Built `llama.cpp:sycl-f16-b10809-clean-85d5703a3` — master `85d5703a3`, `GGML_SYCL_F16=ON`, **no local patches** — from a `git worktree` of `origin/master`, and re-ran the same bench profile on card 2.

| arm | Nemotron decode median | σ | acceptance | outcome |
|---|---|---|---|---|
| patched, run 1 (§5) | — | — | — | **engine reset**, decode run 4 |
| **clean upstream** | 93.06 tok/s | **0.77** | 100.0% | **completed, 20/20** |
| patched, run 2 (retry) | **98.91 tok/s** | 3.94 | 100.0% | **completed, 20/20** |

**The control arm did not settle it, and the retry is why.** The patched image completed a full run immediately after the clean one, so today's tally is **2 faults in 3 patched runs and 0 in 1 clean run** — the fault is *intermittent*, and a single pass per arm cannot distinguish "our patches cause it" from "it happens sometimes". Settling this needs repetition (≥4 runs per arm, counting faults), not another single run. **Do not read the clean pass as exoneration of upstream or conviction of the patch series.**

What the control arm *did* deliver is an attribution of the speed, by running the two production models on it as well:

| model | stock upstream | + our 8-patch series | patches are worth |
|---|---|---|---|
| Ornith 1.5-9B + MTP | 74.99 tok/s | 76.99 | **+2.7% — noise** |
| Gemma 4 E2B + MTP | 174.75 tok/s | 204.45 | **+17.0% — real** |
| Nemotron 30B-A3B + MTP | 93.06 tok/s | 98.91 | +6.3% |

**This reassigns the credit for §3's headline.** Ornith's +25.4% is upstream's 73 commits plus the dropped revert; our SYCL series contributes essentially nothing to it. The series earns its keep on **E2B** (+17%), which is the q4_0 model whose expert/MMVQ paths those patches actually touch. Nemotron's 98.91 is a new high for this rig (previous best 91.91, 2026-08-21).

The DRM nodes were renumbered at the 2026-09-01 03:03 boot and `card0` no longer exists: GPU 0 (`0000:03:00.0`) is now **card1 + renderD128**, GPU 1 (`0000:0b:00.0`) is **card2 + renderD129**, `card3` is the AMD iGPU. Launcher fixed and commented; **any launcher with a hardcoded `/dev/dri/cardN` should be re-derived from `/sys/class/drm/card*/device` before the next restart.**
