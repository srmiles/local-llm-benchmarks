### Rebase: three conflicts, one cause

Upstream [`5320c87`](https://github.com/ggml-org/llama.cpp/commit/5320c87) ("sycl : bound reorder temp memory to 32 MiB") changed every MoE reorder kernel to stage a few experts at a time through a 32 MiB temporary buffer. The old version allocated a buffer the size of the whole tensor, which can be several GB on large MoE models.

Our Q4_0, Q3_K and Q2_K MoE reorder kernels still used the whole-tensor buffer. So each one conflicted at the same place: the comment above `reorder_qw_q5_k_moe`.

The fix was to **port each kernel to upstream's chunked loop, not to keep the old form**. The loop works like this:
- Copy `n_chunk` experts into the temporary buffer.
- Launch the per-block kernel over `blocks_per_expert * n_chunk`, writing to `chunk + e * expert_bytes`.
- Loop over the next chunk. The queue is in-order, so the next copy waits for the previous kernel.

This conversion is mechanical, so it is scripted ([`chunkify.py`](../../configs/benchmarks/20261031-b12017-hf/ab/chunkify.py)). The `opt_for_reorder_id` explicit type list and the `ggml_sycl_mul_mat_vec_q_id_reorder` dispatch cases came through intact. They were checked after the rebase, because a gate that is missing compiles without error and just never takes the reorder path (finding #51 has the same trap). The MMVQ templating refactor [`5cd62ff`](https://github.com/ggml-org/llama.cpp/commit/5cd62ff) merged with no conflict.

## Method

- Card 2 (`level_zero:1`, `0000:0b:00.0`), run through `bench-slot.sh` on `:8020`. `:8011` was stopped for the window and restored by the runner's trap.
- KV cache q8_0, `-fa on`, so the #31125 DPAS FA path runs.
- `bench-candidate.py` as in finding #58: 20 × 300-token decode at temp 0.6 / top-p 0.95 / top-k 20, prefill at 500 / 2K / 5K / 12K.

| Arm | Image |
|---|---|

Rounds r1 and r2 ran all four models. Round r3 ran Ornith and Nemotron only, the two with production slots on card 1 or 2. The arm order changed each round (old/new/clean → new/clean/old → clean/old/new), so the order is not a confound.

Launch settings match production: Ornith Q4_K_M + Q8_0 MTP n-max 3; E2B QAT Q4_0 + Google MTP n-max 3, `MMVQ_MAX_COLS=64`; 26B-A4B Q4_K_M + MTP n-max 5; Nemotron Q4_0 + Q8_0 MTP n-max 7, p-min 0.6.

Reading it:

- **E2B and 26B gain in both rounds, and `clean` gains as much.** The upstream commits between `9ae73e68f` and b12017 do the work. The best candidates on the hot path:
  - #31125 DPAS FA on quantized KV: every slot uses q8_0 KV, which is why `-fa on` matters here.
  - [`bf48103`](https://github.com/ggml-org/llama.cpp/commit/bf48103): vectorized reorder dequant stores, which include Q4_0. E2B and 26B are QAT Q4_0.
  - [`547208d`](https://github.com/ggml-org/llama.cpp/commit/547208d): ESIMD FFN path restored.

  **None of these was isolated.** No `GGML_SYCL_FA_DPAS=0` arm was run, and that is the obvious next control (finding #58 rule (a)).
- **E2B in production is on `9d1878a43`, not on the `old` image.** Its 2026-10-18 figure on that build was 207–212 tok/s, so against what the categorise slots really run, b12017 is about +30%. This is a cross-date comparison, so it is only accurate to about ±10% (finding #40).
- **Ornith: `new` beats `old` in every round on acceptance (+6.7 pt pooled) and on prefill (+8%).** The decode gain (+5%) is inside the noise of an MTP-drafted model, with σ 15–19 (finding #31). Prefill and acceptance are the signals to trust.
- **The local series still helps a little.** `new` vs `clean`: E2B +5.0%, Ornith +2.8%, 26B +2.2%, Nemotron 0. Q4_0/Q3_K/Q2_K MoE reorder is still not upstream.
- **Nemotron does not move.** Its Q4_0 weights are outside both XMX type lists, and most of its 52 layers are Mamba2/SSM, so DPAS FA has few attention layers to act on. The SSM explanation is not profiled. A K-quant is still the open lever (finding #58 rule (c)).
