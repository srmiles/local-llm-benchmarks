# B580 vs B60 head-to-head — Gemma 4 E2B + Google MTP

**Date:** 2026-08-22
**Purpose:** Establish B580 vs B60 baseline as part of the small-services offload migration (task #144). Same model, same build, same launcher pattern, both isolated (pulled from Traefik LB during bench).
**Build:** `llama.cpp:sycl-f16` (b10433, commit `9b05354ec`) — identical image byte-for-byte on both hosts (transferred via `docker save` + NAS + `docker load`, IDs match).
**Model:** Gemma 4 E2B QAT Q4_0 (`/data/llm/gemma-4-E2B-it-GGUF/gemma-4-E2B_q4_0-it.gguf`) + Google official MTP drafter Q8_0 (`/data/llm/gemma-4-E2B-it-assistant-GGUF/gemma-4-E2B-it-assistant-official.bf16.gguf`)
**Bench script:** `/tmp/bench-e2b-fixed.py` — 3-sample per prefill size, warmup + `ignore_eos=true`, greedy decode, `cache_prompt=false`, UUID-prefix per sample.

| **Decode + MTP (greedy 512 tok)** | **159.55 tok/s** | **128.19 tok/s** | **-20%** |
| MTP acceptance rate | ~83% typical | 82.9% (364/439) | ≈ |

| Idle power | ~50W | ~45W | -10% |

**Read:**
- **Prefill parity across the board** — same Battlemage arch, same 456 GB/s memory bandwidth, same FA vec kernel path. Compute-bound prefill saturates on both cards equally.
- **B580 decode ~80% of B60 decode** — the FA/GEMM kernels driving decode are more compute-limited than memory-limited (finding #23: at ~20% BW utilization, kernels are the bottleneck). B580's fewer active Xe cores show up here. This is consistent with the pattern expected for a "consumer" Battlemage part vs the "workstation" Pro variant.
- **MTP acceptance is unaffected** — same target model + same drafter + same quant = same acceptance rate. Nothing hardware-specific there.
- **B580 draws 5W less at idle** — smaller die, fewer active units.

## Why the first bench misled

The first attempt (before pulling from LB) showed B580 at **129 tok/s and B60 at only 92 tok/s** — a 40% B580 advantage. That was a **Traefik LB contention artifact**: with all three backends live in the `llm-categorise` pool (llm.local :8006 + llm.local :8009 + llm2 :8009), other traffic to `https://llm.levirge.com/v1/categorise` was routing to B60 :8009 while the bench was running. The B60 was serving mixed workload, the B580 wasn't. Pulling both from the LB restored the true picture.

**Lesson: isolate BOTH ends of an A/B when comparing hardware across a live LB pool.** Otherwise you measure "how much LB traffic each backend has" as much as "how fast the hardware is."

This mirrors finding #20 (mixing methodologies gives artifacts): here it's mixing bench request with LB traffic. Same class of error, different mechanism.

## Steve's earlier memory of "~130 tps on B60"

Steve recalled B60 E2B running at "around 130 tps," which matches the "some contention" state well:
- Fully isolated, clean cache: 159 tps (today) / 138.8 tps (historical, less warmed)
- Some LB traffic co-serving: ~130 tps
- Full LB traffic co-serving: 92 tps (today's contended bench) / 71.5 tps (README prod row)

The full range is 90–160 tps depending on how much concurrent load the container is serving.

## Practical implications for the migration (task #144)

**B580 as the small-services host is still the right call**, but the framing changes slightly:

1. **B580 is a modest downgrade for individual small-service performance** (~20% slower decode on E2B). It's not "faster and smaller" — just "smaller and still-plenty-fast."
2. **The migration win is on the B60 side, not the B580 side.** Freeing both B60s to host **Nemotron 3.5 Lightning 30B-A3B** (or similar single-card 24 GB workload) is the actual payoff. Task #142 alternative (tensor-split Ornith 1.5-35B-A3B) is off the table per finding #24 anyway.
3. **12 GB VRAM headroom is fine for the intended workload:** embed (0.5 GB) + rerank (1.4 GB) + E2B (3.4 GB) + overhead = 5.6 GB used, 6.4 GB free. Plenty of room for a future 4th small service or LMCache-style prefix store.
4. **Real-world impact is negligible.** Brain-eval effective rate on E2B categorise is <10 tps sustained (bottlenecked upstream on ingest/judge), so 128 vs 159 tps decode is not the constraint.

**One gotcha discovered during setup**: the categorise launcher inherited from llm.local uses `--device /dev/dri/card1 --device /dev/dri/renderD128`. On llm.local B60 that's the card 1 render node; on llm2 the same names resolve to the B580 card + iGPU render node. Passing the iGPU's render node causes SYCL to enumerate the UHD 630 (unsupported for compute), triggering "No device of requested type available" — same signature as our earlier E2B wedge investigation on B60. Fix: full `--device /dev/dri` passthrough. Same fix pattern already applied to the other card-2 launchers on llm.local. Now documented as part of finding #15 companion.
